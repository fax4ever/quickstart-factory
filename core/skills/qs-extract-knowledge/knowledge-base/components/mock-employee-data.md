# Mock Employee Data

## Overview

A zero-dependency Python library that provides a hardcoded dictionary of mock employee and IT asset records. It acts as the single source of truth for employee data across multiple mock services in the it-self-service-agent quickstart, consumed as a local path dependency by mock-service-now, zammad-bootstrap, servicenow-bootstrap, and the evaluations test harness. It supports runtime injection of additional test users via the `TEST_USERS` environment variable.

## Tech Stack & Dependencies

- **Runtime:** Python >= 3.12
- **Build system:** Hatchling (PEP 517)
- **Container image:** None (library only, not independently deployed)
- **Key dependencies:** None at runtime (zero `dependencies` in pyproject.toml)
- **Dev dependencies:** pytest, pytest-asyncio, pytest-cov, black, flake8, isort, mypy
- **Helm subchart:** N/A (data is injected via `TEST_USERS` env var wired through Helm values)

## Key Patterns

### Shared Local Path Dependency

The library is consumed by other components as a local path dependency using hatchling's path resolution. Each consumer references it in their `pyproject.toml`:

```toml
# From mock-service-now/pyproject.toml
[tool.hatch.metadata]
allow-direct-references = true

mock-employee-data = { path = "../mock-employee-data" }
```

The `requirements.txt` is auto-generated by `uv export` and simply contains `-e .` (editable self-install).

### Hardcoded Data Dictionary with Email-Keyed Lookup

Employee data is stored as a module-level Python dictionary keyed by email address. Each record contains employee identity fields, laptop asset details, and ServiceNow-compatible status fields (`sys_id`, `install_status`, `operational_status`):

```python
# From mock-employee-data/src/mock_employee_data/data.py
MOCK_EMPLOYEE_DATA = {
    "alice.johnson@company.com": {
        "employee_id": "1001",
        "sys_id": "1001",
        "name": "Alice Johnson",
        "email": "alice.johnson@company.com",
        "laptop_model": "Latitude 7420",
        "warranty_status": "Expired",
        # ... asset tracking fields
    },
    # 14 employees total across EMEA, LATAM, APAC regions
}
```

### Runtime Test User Injection via TEST_USERS

The `get_employee_data()` function merges the hardcoded dictionary with dynamically generated records for emails specified in the `TEST_USERS` environment variable. This lets real user emails be injected at deploy time for demo scenarios without modifying source code:

```python
# From mock-employee-data/src/mock_employee_data/data.py
def get_employee_data() -> Dict[str, Dict[str, Any]]:
    result = MOCK_EMPLOYEE_DATA.copy()
    test_users_env = os.getenv("TEST_USERS")
    if not test_users_env:
        return result
    test_emails = [
        email.strip() for email in test_users_env.split(",") if email.strip()
    ]
    for idx, email in enumerate(test_emails):
        if email.lower() in result:
            continue
        employee_id = 9001 + idx
        user_data = _generate_user_data_for_email(email, employee_id)
        result[email.lower()] = user_data
    return result
```

### Module-Level Caching in Consumers

Consumers call `get_employee_data()` once at module load and cache the result to ensure consistency across the session:

```python
# From mock-service-now/src/mock_servicenow/data.py
from mock_employee_data import get_employee_data

EMPLOYEE_DATA = get_employee_data()
```

## Configuration

- **Environment variables:**
  - `TEST_USERS`: Comma-separated list of email addresses to inject as additional mock employees at runtime. Generated users get `sys_id` starting from 9000, employee IDs from 9001, and serial numbers prefixed with `TEST`. Wired through Helm as `testUsers` in `helm/values.yaml` line 317.
- **Config files:** None
- **Helm values:** `testUsers` in `helm/values.yaml` is passed through as the `TEST_USERS` env var to consuming pods

## Known Gotchas

- Generated test user records use `random.randint` for purchase dates (1-3 years ago), so warranty status and dates are non-deterministic across restarts. The `sys_id` values (9000+) and employee IDs (9001+) are deterministic based on index position in the comma-separated list.
- Duplicate email detection uses `email.lower()` comparison against existing keys, but the hardcoded dictionary uses lowercase email keys throughout. If `TEST_USERS` contains an email matching a hardcoded entry, it is silently skipped rather than overriding the original.
- The `requirements.txt` is generated by `uv export --no-dev` and only contains `-e .` (self-install). Consumers must have the `mock-employee-data/` directory available at the expected relative path at install time.

## Testing Notes

- Tests use direct `os.environ` manipulation to set/unset `TEST_USERS` and verify three scenarios: no test users, with test users, and deduplication of existing users
- Run tests with `pytest` from the `mock-employee-data/` directory
- The test file (`tests/test_get_employee_data.py`) has a typo: `except AssertionError` instead of `except AssertionError` -- but this does not affect pytest execution since pytest catches assertions directly
