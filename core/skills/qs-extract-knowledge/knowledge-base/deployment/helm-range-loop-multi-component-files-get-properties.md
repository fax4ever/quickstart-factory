# Helm Range Loop Multi-Component Chart with Files.Get Properties

## Overview

A Helm chart pattern where all Kubernetes resources (Deployment, Service, Route, PVC, ServiceMonitor, ConfigMap) are generated by iterating a `values.components` map. Each component's Quarkus application properties are loaded from files embedded in the chart directory via `$.Files.Get`, creating per-component ConfigMaps. The chart is flat (no subchart dependencies) and uses OpenShift-specific features like ImageStreamTag triggers and Routes.

## Pattern Description

Instead of creating separate template files per microservice, this chart defines a single `deployment.yaml`, `service.yaml`, `route.yaml`, `pvc.yaml`, `servicemonitor.yaml`, and `configmap.yaml` -- each template iterates `range $name, $component := .Values.components` and emits one Kubernetes resource per enabled component. Per-component Quarkus properties files are stored under `chart/properties/<component-name>/application-prod-quarkus.properties` and loaded at render time via `$.Files.Get`. This approach allows adding new components by only editing `values.yaml` and adding a properties file.

## Implementation

### Component Definitions in Values

Each component specifies its resource requirements, deployment strategy, and optional features:

```yaml
# chart/values.yaml
namespace: slog-analyzer
imageRegistry: image-registry.openshift-image-registry.svc:5000

components:
  correlator:
    enabled: true
    replicas: 1
    memoryLimit: 512Mi
    strategy: RollingUpdate
    expose: false
    storage: {}
  analyzer:
    enabled: true
    replicas: 1
    memoryLimit: 512Mi
    strategy: RollingUpdate
    expose: false
    secrets:
      - openai
    serviceCa:
      enabled: true
      configMap: service-ca-bundle
  ui-console:
    enabled: true
    replicas: 1
    memoryLimit: 512Mi
    strategy: Recreate
    expose: true
    storage:
      mountPath: /storage
      size: 1Gi
```

### ConfigMap from Files.Get

Per-component properties files are loaded from the chart directory and rendered into ConfigMaps:

```yaml
# chart/templates/configmap.yaml
{{- range $name, $component := .Values.components }}
{{- if $component.enabled }}
{{- $propsFile := printf "properties/%s/application-prod-quarkus.properties" $name }}
{{- $props := $.Files.Get $propsFile }}
{{- if $props }}
---
apiVersion: v1
kind: ConfigMap
metadata:
  name: {{ $name }}-config
data:
  application.properties: |
{{ $props | indent 4 }}
{{- end }}
{{- end }}
{{- end }}
```

### ImageStreamTag Trigger Annotation

Deployments use OpenShift ImageStream triggers so that new image pushes automatically trigger rollouts:

```yaml
# chart/templates/deployment.yaml
annotations:
  image.openshift.io/triggers: >-
    [{"from":{"kind":"ImageStreamTag","name":"{{ $name }}:latest"},
      "fieldPath":"spec.template.spec.containers[?(@.name==\"{{ $name }}\")].image"}]
```

### Config Checksum for Rolling Updates

The deployment template includes a checksum annotation to trigger pod restarts when ConfigMap content changes:

```yaml
# chart/templates/deployment.yaml
template:
  metadata:
    annotations:
      checksum/config: {{ include (print $.Template.BasePath "/configmap.yaml") $ | sha256sum }}
```

### Conditional Features per Component

Components can optionally declare secrets to mount, storage volumes, and extra environment variables:

```yaml
# chart/templates/deployment.yaml (secret mounting)
{{- if $component.secrets }}
{{- range $component.secrets }}
- secretRef:
    name: {{ . }}
{{- end }}
{{- end }}

# Extra env vars
{{- if $component.extraEnv }}
{{- toYaml $component.extraEnv | nindent 12 }}
{{- end }}
```

### Conditional Route and PVC

Routes and PVCs are only created for components that declare them:

```yaml
# chart/templates/route.yaml
{{- range $name, $component := .Values.components }}
{{- if and $component.enabled $component.expose }}
---
apiVersion: route.openshift.io/v1
kind: Route
# ...
{{- end }}
{{- end }}
```

## Configuration

- **Key settings:** `imageRegistry` (defaults to internal OpenShift registry); per-component `enabled`, `replicas`, `memoryLimit`, `strategy`, `expose`, `storage`, `secrets`, `serviceCa`, `extraEnv`
- **Defaults:** All components enabled with 1 replica and 512Mi memory limit; only `ui-console` is exposed via Route; only `ui-console` has PVC storage; only `analyzer` mounts the `openai` secret
- **Dependencies:** Images must be pre-built and pushed to ImageStreams (handled by Tekton pipeline); `infra-endpoints`, `otel-infra-endpoints` ConfigMaps and `infra-accounts` Secret must exist; `service-ca-bundle` ConfigMap must exist if `serviceCa.enabled` is true

## Gotchas

- The `nettyWorkaround: true` setting in values.yaml appends `-Dio.netty.transport.noNative=true` to JAVA_OPTS_APPEND for all components -- this works around a Netty native transport issue on OpenShift (see `chart/values.yaml` lines 41-42)
- The ConfigMap checksum annotation hashes the entire `configmap.yaml` template output, not individual component configs -- any component's property change triggers a rollout of all components
- The `$.Files.Get` path is relative to the chart root -- properties must be stored in `chart/properties/<name>/` not at the repo root, and the path is constructed dynamically from the component name
- Images are referenced via the internal OpenShift registry (`image-registry.openshift-image-registry.svc:5000`) combined with `namespace` and component name -- this only works within the cluster and requires ImageStreams to be created by the build pipeline
