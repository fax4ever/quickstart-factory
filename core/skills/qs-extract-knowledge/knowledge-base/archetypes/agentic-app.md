# Agentic App

## Overview

An agentic app deploys one or more AI agents that can reason, use tools, and take actions to accomplish tasks on behalf of users. Unlike simple chat interfaces that only generate text, agentic apps integrate tool ecosystems (web search, databases, external APIs) and can orchestrate multi-step workflows. On RHOAI, these apps leverage model serving for LLM inference while the agent orchestration layer manages tool dispatch, conversation state, and safety guardrails.

## Typical Components

- **Model serving:** vLLM or LlamaStack for LLM inference (chat completions with tool/function calling support)
- **Backend:** FastAPI handling agent lifecycle, session management, and streaming responses
- **Frontend:** React/PatternFly providing agent configuration UI and real-time chat with SSE streaming
- **Data layer:** PostgreSQL for agent/session persistence, pgvector for knowledge base vector search
- **Supporting:** MCP servers for tool integration, guardrails for safety controls, ingestion pipelines for knowledge bases

## When to Use

- **Business problem:** Automating customer interactions or internal workflows that require the AI to take actions (search the web, query databases, call APIs) rather than just answer questions from static knowledge
- **RHOAI capabilities:** Demonstrates model serving with tool/function calling, agent orchestration across multiple frameworks, MCP protocol for extensible tool integration, and configurable guardrails
- **Scale/complexity:** Medium to high complexity; suitable when a simple prompt-response flow is insufficient and the application needs multi-step reasoning with external tool invocations

## Decision Criteria

### vs rag-chatbot

Pick **agentic-app** when the AI needs to take actions beyond retrieval -- calling external APIs, executing multi-step workflows, or using tools dynamically selected at runtime. Pick **rag-chatbot** when the primary interaction is question-answering grounded in uploaded documents, without tool orchestration or multi-step agent reasoning.

### vs model-serving-app

Pick **agentic-app** when the application includes an orchestration layer that manages agent state, tool dispatch, and multi-turn reasoning on top of the served model. Pick **model-serving-app** when the focus is on deploying and exposing a model endpoint (KServe/vLLM) without an agent framework wrapping it.

## Approach B: Event-Driven Agent Pipeline (from ansible-log-analysis)

### When to Use

When the agentic app is triggered by external events (alerts, webhooks, log streams) rather than user conversations, and the agent follows a domain-specific multi-step pipeline (detect, classify, route, gather context, remediate) rather than open-ended conversational tool use.

### Differences from Approach A

- **Triggering model:** Approach A is user-initiated (conversational chat); Approach B is event-driven (Grafana alerts trigger the pipeline via webhook to `backend-inference-webhook` in `deploy/helm/ansible-log-monitor/values.yaml`)
- **Agent framework:** Approach A supports pluggable multi-framework runners (LlamaStack, LangGraph, CrewAI); Approach B uses LangGraph exclusively with a fixed multi-step graph (`src/alm/agents/graph.py`)
- **Agent topology:** Approach A has a single agent with tool access; Approach B composes a main graph with nested sub-agents -- a `get_more_context_agent` that decides whether to invoke a `loki_agent` sub-graph for additional log retrieval (`src/alm/agents/get_more_context_agent/graph.py`, `src/alm/agents/loki_agent/graph.py`)
- **Pipeline structure:** Approach B follows a fixed domain-specific flow: cluster logs -> summarize -> classify error type -> route to expert domain -> decide if more context needed -> query Loki via MCP -> summarize Loki context -> generate step-by-step solution (`src/alm/agents/graph.py`)
- **MCP usage:** Both use MCP, but differently -- Approach A uses MCP servers as general-purpose tool providers; Approach B uses a custom `MCPClient` class (`src/alm/mcp/mcp_client.py`) to query a Loki MCP server for domain-specific log retrieval with JSON-RPC 2.0 protocol
- **Tool definition:** Approach B defines LangChain `@tool`-decorated functions for specific Loki query patterns (file logs, text search, play recaps, log lines above) in `src/alm/tools/loki_tools.py`
- **Model serving:** Approach A deploys vLLM/LlamaStack for self-hosted inference; Approach B connects to any OpenAI-compatible endpoint via `OPENAI_API_ENDPOINT` env var (`src/alm/llm.py`), with a separate endpoint for tool-calling-capable models (`OPENAI_API_ENDPOINT_WITH_TOOL_CALLING`)
- **RAG integration:** Approach A uses pgvector for knowledge base vector search; Approach B uses a separate FAISS-based RAG service (`services/rag/`) with HuggingFace TEI for embeddings, providing "cheat sheet" context from Ansible error documentation PDFs
- **Frontend:** Approach A uses React/PatternFly; Approach B uses Gradio for both the main UI (`services/ui/`) and an annotation/evaluation interface (`services/annotation_interface/`) with DeepEval
- **Observability:** Approach A has no built-in observability; Approach B includes Arize Phoenix for LLM tracing (`src/alm/utils/phoenix.py`), Grafana for dashboards, and Alloy for log ingestion (`services/alloy/`)
- **Log management stack:** Approach B includes a full log management pipeline -- Grafana Alloy collects logs from AAP clusters, Loki stores and indexes them, Grafana provides alerting on error patterns, and the agent queries Loki via MCP for additional context

### Typical Components

- **Model serving:** Any OpenAI-compatible API endpoint (RHOAI model serving, external LLM), with separate endpoint option for tool-calling models
- **Backend:** FastAPI (`src/alm/`) with LangGraph agent orchestration, MCP client for Loki tool integration, LangChain tools
- **Frontend:** Gradio UI for log analysis dashboard (`services/ui/`), Gradio annotation interface with DeepEval for evaluation (`services/annotation_interface/`)
- **Data layer:** PostgreSQL for alert/metadata persistence, FAISS for RAG vector storage (Ansible error documentation), Loki for time-series log storage
- **Supporting:** HuggingFace TEI for text embeddings, MinIO for object storage, Arize Phoenix for LLM tracing, Grafana + Alloy for log ingestion and alerting, MCP server for Loki queries, sentence-transformers + scikit-learn for log clustering (`services/clustering/`)

## Approach C: Framework-less MCP-Native Agent with Provider Abstraction (from data-governance-co-pilot)

### When to Use

When the agentic app needs direct control over the agentic loop without framework dependencies, connects to a single specialized MCP server for domain-specific tool use (e.g., database governance), and benefits from the ability to switch between a self-managed agentic loop (MCP-Direct) and a delegated orchestration mode (Llama Stack) via a provider abstraction layer.

### Differences from Approach A

- **Agent framework:** Approach A uses pluggable framework runners (LlamaStack, LangGraph, CrewAI); Approach C uses no agent framework in MCP-Direct mode -- the agentic loop is hand-coded in `packages/copilot/src/copilot/providers/mcp_direct.py` using the MCP SDK (`mcp.ClientSession`) and OpenAI SDK (`AsyncOpenAI`) directly, with an alternative Llama Stack provider (`packages/copilot/src/copilot/providers/llama_stack.py`) that delegates orchestration to Llama Stack's Agents API
- **Provider abstraction:** Approach C introduces a `LLMProvider` abstract base class (`packages/copilot/src/copilot/providers/base.py`) with `MCPDirectProvider` and `LlamaStackProvider` implementations, switchable via the `COPILOT_PROVIDER_MODE` environment variable (`packages/copilot/src/copilot/providers/factory.py`); Approach A uses pluggable runners within a single framework
- **MCP integration:** Approach A uses MCP servers as general-purpose tool providers; Approach C connects to a single specialized MCP server (EDB's `pg-airman-mcp` for PostgreSQL) via the official MCP SDK's `streamablehttp_client` transport (`packages/copilot/src/copilot/providers/mcp_direct.py` line 31), with MCP tool definitions automatically converted to OpenAI function calling format (`_convert_mcp_tools_to_openai` method)
- **Tool security:** Approach C implements a hard-coded tool allowlist with Pydantic schema validation in `packages/copilot/src/copilot/providers/tool_validation.py` -- every tool call is validated against `ALLOWED_TOOLS` set and type-checked via Pydantic models (`ExecuteSqlArgs`, `ListObjectsArgs`, etc.) before execution, with fail-closed behavior (unknown tools are rejected even if MCP server advertises them); Approach A delegates tool validation to the framework runners
- **Model format detection:** Approach C supports two tool calling formats -- Nemotron's custom `<TOOLCALL>` tags parsed by `_parse_nemotron_tool_calls()` and standard OpenAI function calling -- with auto-detection from model name (`_detect_tool_call_format` in `mcp_direct.py`); configurable via `LLM_TOOL_CALL_FORMAT` env var (`auto`/`nemotron`/`openai`)
- **Governance policy:** Approach C makes data governance policy a first-class concept -- policies can be uploaded/deleted via REST API (`/policy/upload`, `/policy/status`, `/policy/delete` in `service.py`), injected into the system prompt dynamically for MCP-Direct mode (no conversation restart needed), or trigger agent recreation for Llama Stack mode (requires conversation restart per `requires_conversation_restart_on_policy_update()`)
- **MCP session resilience:** Approach C includes MCP session reconnection logic (`_reconnect_mcp` method) and retry with exponential backoff (`_retry_mcp_operation` method) for handling pod restarts and transient failures
- **Thinking tag handling:** Approach C handles Nemotron's `<think>` and `</think>` tags during streaming, separating LLM reasoning from user-facing content, with support for both `enable_reasoning=True` (show thinking) and `enable_reasoning=False` (silently discard via Nemotron's `/no_think` instruction)
- **Frontend:** Approach A uses React/PatternFly; Approach C uses SvelteKit with Vega-Lite for inline data visualizations (bar charts, pie charts, line charts) generated by the LLM in `vega-lite` code blocks (`packages/copilot/src/copilot/providers/mcp_direct.py` system prompt lines 433-466)
- **Model options:** Approach C supports two models -- NVIDIA Nemotron Nano 9B v2 (9B params, custom TOOLCALL format, MCP-Direct only) and Qwen3-14B AWQ (14B params, OpenAI function calling, both modes) -- deployed via KServe + vLLM (`helm/nemotron-model/`, `helm/qwen3-model/`)

### Typical Components

- **Model serving:** KServe + vLLM deploying either NVIDIA Nemotron Nano 9B v2 or Qwen3-14B AWQ; optional Llama Stack Distribution for delegated agent orchestration (`helm/copilot-llama-stack/`)

## Approach F: Multi-Persona Agent Platform with Compliance Controls (from multi-agent-loan-origination)

### When to Use

When the agentic app serves a regulated industry (financial services, healthcare, legal) and requires multiple persona-specific agents each with distinct tool sets and data access scopes, Keycloak-based RBAC that controls which tools each role can invoke, compliance knowledge retrieval with regulatory source tiering, tamper-evident audit trails, PII masking based on user role, human-in-the-loop decision gates, and vision-based document extraction -- all deployed as a full-stack monorepo with React frontend and FastAPI backend.

### Differences from Approach A

- **Agent topology:** Approach A has a single agent with tool access and pluggable framework runners; Approach F deploys 5 distinct LangGraph agents -- `public-assistant` (product info, affordability), `borrower-assistant` (application intake, document tracking, disclosure management), `loan-officer-assistant` (pipeline review, document quality, underwriting submission), `underwriter-assistant` (risk assessment, compliance checks, conditions, decisions), and `ceo-assistant` (analytics, masked-PII portfolio view) -- each defined by a YAML config in `config/agents/` with its own system prompt, tool list, and `model_routing.strategy`
- **Agent selection:** Approach A selects agents via user choice in the UI; Approach F routes to the correct agent based on the authenticated user's Keycloak role -- each chat endpoint (`routes/borrower_chat.py`, `routes/underwriter_chat.py`, etc.) maps to one agent, and the JWT token's role claim determines which endpoints the user can access
- **RBAC-scoped tool access:** Approach A delegates tool access to the framework; Approach F defines per-tool `allowed_roles` lists in each agent's YAML config (e.g., `kb_search` is restricted to `[loan_officer, underwriter, admin]`, `uw_render_decision` to `[underwriter, admin]`); the `AgentState` carries `tool_allowed_roles` and `user_role` fields through the LangGraph graph, and tools check authorization before execution

## Approach H: Two-Phase Deterministic-Then-Agentic Pipeline with REST Tool Discovery (from portfolio-manager-agent)

### When to Use

When the agentic app follows a two-phase workflow -- a deterministic pipeline that runs domain-specific steps in sequence (parse documents, build output, validate against constraints, retry on failure) followed by an interactive agentic chat where the LLM selects tools to modify the pipeline output -- and uses a lightweight REST-based HTTP tool discovery protocol instead of MCP or an agent framework, with Flask as the backend and KServe-served ML models as supporting tool components.

### Differences from Approach A

- **Two-phase architecture:** Approach A provides open-ended conversational tool use from the start; Approach H separates into Phase 1 (deterministic pipeline: parse guidelines -> build portfolio -> calculate VaR -> retry if VaR exceeds threshold up to `MAX_PORTFOLIO_ATTEMPTS = 10` -> draft email via LLM) and Phase 2 (agentic chat where the LLM selects tools to modify holdings while respecting frozen compliance constraints from Phase 1) -- the UI calls granular orchestrator endpoints in sequence (`/pipeline/guidelines`, `/pipeline/portfolio`, `/pipeline/var`, `/pipeline/email`) for real-time progress feedback, or `/pipeline` for the full pipeline (`orchestrator/src/app.py`)
- **Agent framework:** Approach A uses pluggable multi-framework runners (LlamaStack, LangGraph, CrewAI); Approach H uses no framework -- the `Orchestrator` class in `orchestrator/src/orchestrator.py` implements the agentic loop directly using OpenAI SDK `chat.completions.create` with tool calling, iterating up to 20 LLM calls (`llm_count < 20`) until no tool calls are returned
- **Tool discovery protocol:** Approach A uses MCP servers for tool integration; Approach H uses a custom REST-based HTTP protocol where each tool agent exposes `GET /tools` returning a JSON array of tool schemas (`name`, `description`, `parameters` as JSON Schema) and `POST /tools/<tool_name>` for execution -- the `HttpToolServer` class in `orchestrator/src/orchestrator.py` implements this protocol, and `DiscoveredTool` dataclass maps each tool to its hosting server; tools are auto-converted to OpenAI function calling format via `tools_payload()`
- **Tool agent architecture:** Approach A integrates tools within a single service; Approach H deploys 3 separate Flask tool agents as independent services -- `tools/value_at_risk/src/app.py` (portfolio VaR calculation via yfinance market data and scipy parametric method at 99% confidence), `tools/portfolio/src/app.py` (equal-weight equity portfolio construction from S&P 100 excluding prohibited symbols via yfinance), and `tools/guidelines/src/app.py` (investment guideline PDF parsing with prohibited ticker extraction) -- each advertising its tools via a `TOOLS` list and serving them on separate ports (7001, 7002, 7003)
- **ML model as tool component:** Approach H uses a KServe InferenceService with MLServer scikit-learn runtime to serve an MLP classifier (`deploy/helm/templates/inferenceservice-guidelines-mlp.yaml`, `deploy/helm/templates/servingruntime-mlserver.yaml`) that classifies guideline sentences as prohibition-related; the guidelines tool agent calls this InferenceService at `INFERENCE_URL` (default `http://guidelines-mlp:80`) to extract prohibited ticker symbols; Approach A does not use KServe-served ML classification models as tool components
- **Backend framework:** Approach A uses FastAPI; Approach H uses Flask for both the orchestrator (`orchestrator/src/app.py`) and all 3 tool agents, with Flask-CORS for cross-origin support
- **Tool filtering:** Approach H supports phase-specific tool subsets via `refresh_tools_filtered(allowed_names)` -- Phase 2 chat restricts tools to `PHASE2_TOOLS = {"portfolio_equities", "portfolio_replace_symbol", "value_at_risk"}`, preventing the agentic chat from re-parsing guidelines or calling tools outside the portfolio modification scope (`orchestrator/src/app.py`)
- **Frozen compliance constraints:** Approach H passes the `prohibited_tickers` list from Phase 1's guideline parsing into Phase 2's portfolio context as `symbols_exclusion`, ensuring the LLM cannot violate compliance constraints established in the deterministic pipeline; `disliked_symbol_in_message()` in `pipeline.py` detects when a user rejects a specific ticker in chat, and `apply_symbol_rejection()` handles the replacement while maintaining the exclusion list
- **Context injection:** Approach H injects the full portfolio context (portfolio holdings, VaR, prohibited tickers, pipeline inputs) as a JSON block in the system prompt for Phase 2 chat via `chat_with_context()`, with an `on_tool_result` callback that updates the context object after each tool call via `apply_phase2_tool_result()` (`orchestrator/src/app.py`, `pipeline.py`)
- **Guardrails:** Approach A has configurable guardrails within the agent framework; Approach H uses NeMo Guardrails via TrustyAI `NemoGuardrails` CR (`deploy/helm/templates/nemoguardrails-cr.yaml`) with a separate guardrails service exposing `/v1/guardrail/checks` API; the orchestrator calls `gr.check_input()` before sending user messages to the LLM and `gr.check_output()` before returning LLM responses; guardrails are configured via ConfigMap (`deploy/helm/templates/configmap-guardrails.yaml`) with sensitive data detection (credit cards, SSN, phone numbers), regex patterns (passwords, secrets, API keys), and a custom `check_financial_topic` action that blocks off-topic messages; gracefully degrades -- if `GUARDRAILS_URL` is unset or unreachable, all messages pass through (`orchestrator/src/guardrails.py`)
- **Serverless tool agents:** Approach H optionally deploys portfolio and risk tool agents as Knative Services (`deploy/helm/templates/ksvc-portfolio.yaml`, `deploy/helm/templates/ksvc-risk.yaml`) with configurable min/max scale and concurrency, controlled by `serverless.enabled` Helm value; Approach A does not offer Knative serverless for tool components
- **Model serving:** Approach A deploys vLLM/LlamaStack for self-hosted LLM inference; Approach H is model-server-agnostic for the LLM -- connects to any OpenAI-compatible endpoint via `llmUrl`, `model`, and `apiKey` passed per-request from the frontend (`parse_llm_config()` in `app.py`); additionally serves the scikit-learn MLP via KServe + MLServer as a separate model serving concern
- **Frontend:** Approach A uses React/PatternFly; Approach H uses React + Vite + TypeScript (`frontend/`) with two tabs -- one for deterministic pipeline execution with step-by-step progress (guideline parsing, portfolio building, VaR calculation, email drafting) and one for agentic portfolio chat
- **Model storage:** Approach H uses MinIO for scikit-learn model storage (S3-compatible, with a `job-model-upload.yaml` Job to upload the MLP model to S3), different from Approach A's model storage approach
- **Observability:** Neither Approach A nor Approach H includes built-in observability; Approach H tracks per-request metrics in the response payload (`usage_tokens_in`, `usage_tokens_out`, `llm_count`, `latency_sec`, `tool_history`)

### Typical Components

- **Model serving:** KServe InferenceService with MLServer scikit-learn runtime (`mlserver-sklearn`) for investment guideline MLP classifier (RawDeployment mode, S3/MinIO model storage); any OpenAI-compatible LLM endpoint for chat reasoning and email drafting (tested with Llama 3.3 70B quantized)
- **Backend:** Flask orchestrator (`orchestrator/src/`) implementing REST-based HTTP tool discovery protocol and OpenAI SDK function calling agentic loop; 3 Flask tool agents -- value-at-risk calculator (`tools/value_at_risk/src/`, yfinance + scipy parametric VaR at 99% confidence), portfolio builder (`tools/portfolio/src/`, equal-weight S&P 100 portfolio construction via yfinance), and guideline parser (`tools/guidelines/src/`, PDF parsing with MLP-based prohibited ticker extraction via pdfminer + KServe InferenceService)
- **Frontend:** React + Vite + TypeScript (`frontend/`) with two-tab UI for deterministic pipeline execution and agentic portfolio chat
- **Data layer:** None -- no persistent data store required; portfolio state maintained in-memory per request and passed through context objects
- **Supporting:** MinIO for scikit-learn model storage (S3-compatible); NeMo Guardrails via TrustyAI `NemoGuardrails` CR with sensitive data detection (credit cards, SSN, phone), regex patterns, and custom `check_financial_topic` off-topic blocking action; optional Knative Services for serverless auto-scaling of portfolio and risk tool agents; Kubernetes Job for model upload to MinIO

## Approach I: NVIDIA AI-Q Blueprint Multi-Agent Research System (from rh-research)

### When to Use

When the agentic app is a multi-depth research system that classifies user intent and routes between fast bounded research (shallow) and long-running multi-phase report generation (deep), with the entire agent topology, tool set, LLM configuration, and routing behavior defined declaratively in YAML via NVIDIA NeMo Agent Toolkit, and deep research executed as async jobs using LangChain Deep Agents with citation-backed report output.

### Differences from Approach A

- **Agent framework:** Approach A uses pluggable multi-framework runners (LlamaStack, LangGraph, CrewAI); Approach I uses NVIDIA NeMo Agent Toolkit (NAT) as the top-level framework for workflow registration, component wiring, and evaluation, with LangGraph for orchestration graph construction (`ChatResearcherAgent` builds a `StateGraph` in `src/aiq_agent/agents/chat_researcher/`) and LangChain Deep Agents (`deepagents` library) for deep research runtime (`src/aiq_agent/agents/deep_researcher/deepagents_runtime.py` implements `DeepAgentsRuntime` with `CompositeBackend`, `StateBackend`, and `BaseSandbox`)
- **Declarative YAML workflow:** Approach A configures agents through code and environment variables; Approach I defines the entire workflow in YAML config files (`configs/config_web_default_llamaindex.yml`, `configs/config_domain_routing_and_skills.yml`, `configs/config_frontier_models.yml`) -- LLMs, agents, tools, routing behavior, data sources, and front-end settings are all declarative with `_type` discriminators for component registration and `${ENV_VAR:-default}` for environment interpolation
- **Intent-routed multi-depth research:** Approach A provides open-ended conversational tool use; Approach I routes through an orchestrator (`ChatResearcherAgent` in `src/aiq_agent/agents/chat_researcher/`) that classifies intent (meta vs research via `intent_classifier` agent), routes to shallow or deep research based on complexity, supports optional escalation from shallow to deep (`enable_escalation: true`), and handles clarification questions (`enable_clarifier: true`) -- the orchestrator uses LangGraph `StateGraph` with `Command` objects for conditional routing
- **Shallow vs deep research agents:** Approach A has a single agent with tool access; Approach I has two distinct research agents -- `ShallowResearcherAgent` (`src/aiq_agent/agents/shallow_researcher/agent.py`) uses LangGraph with `ToolNode` and `tools_condition` for bounded tool-calling research with `max_llm_turns: 10` and `max_tool_iterations: 5`, while `DeepResearcherAgent` (`src/aiq_agent/agents/deep_researcher/agent.py`) uses the `deepagents` library for multi-phase workflow (planning, parallel source research, report writing) with `DEFAULT_MAX_RESEARCH_CONCURRENCY = 6` and configurable sandbox execution via Modal
- **Data source registry:** Approach A integrates tools directly or via MCP servers; Approach I uses a centralized `data_source_registry` (`_type: data_source_registry` in YAML config) that controls UI toggles, per-message source filtering in API payloads, and automatic tool inheritance by agents -- agents with no explicit `tools` list inherit all tools from the registry, and `exclude_tools` allows per-agent specialization (e.g., shallow gets `web_search_tool`, deep gets `advanced_web_search_tool`)
- **Model serving:** Approach A deploys vLLM/LlamaStack for self-hosted inference; Approach I uses API-only model serving via NVIDIA NIM endpoints (`base_url: "https://integrate.api.nvidia.com/v1"`) with models like `nvidia/nemotron-3-super-120b-a12b` and `openai/gpt-oss-120b`; multiple LLMs are configured for different roles (intent classification, shallow research, deep research orchestration/planning/writing, document summarization) with per-LLM temperature, top_p, max_tokens, and retry settings
- **Async job architecture:** Approach A handles requests synchronously with SSE streaming; Approach I runs deep research as async jobs via Dask workers (`DASK_NWORKERS`, `DASK_NTHREADS` env vars, `frontends/aiq_api/src/aiq_api/jobs/runner.py`) with NAT `JobStore` for job metadata/status persistence (`NAT_JOB_STORE_DB_URL`), `EventStore` for SSE event streaming (`frontends/aiq_api/src/aiq_api/jobs/event_store.py`), `CancellationMonitor` for graceful job termination, job ownership, and configurable job expiry (`expiry_seconds: 86400`)
- **Citation verification:** Approach I includes built-in citation verification and report sanitization (`src/aiq_agent/common/citation_verification.py`) -- the `SourceRegistry` tracks sources from tool results, `verify_citations` validates that report citations reference actual sources, and `sanitize_report` removes unverified citations; the shallow researcher appends minimal citations when the model omits references (`_append_minimal_citation` in `src/aiq_agent/agents/shallow_researcher/agent.py`)
- **Evaluation harnesses:** Approach A does not include evaluation; Approach I ships 3 evaluation harnesses registered as NAT evaluators (`frontends/benchmarks/`) -- FreshQA (`freshqa/src/evaluator.py`) implementing FreshEval Relaxed methodology with accuracy metrics across fact types, premise types, question complexity, and time periods; DeepResearch Bench and DeepSearch QA for research quality measurement
- **Tokenomics profiling:** Approach I includes tokenomics cost/latency analysis (`src/aiq_agent/tokenomics/`) -- `parse_trace` converts NAT profiler traces to `RequestProfile` objects with per-phase stats (orchestrator, planner, researcher), `PricingRegistry` computes cost from model-specific pricing configurations, and reports combine token counts with cache hit rates
- **Portable agent skill:** Approach I ships `skills/aiq-research/` (`skills/aiq-research/SKILL.md`) so compatible coding harnesses (e.g., LangChain Deep Agents) can invoke AI-Q for routed chat and async deep research jobs without running the full application
- **Frontend:** Approach A uses React/PatternFly; Approach I uses Next.js with NVIDIA Foundations React Core and Tailwind (`frontends/ui/`) with WebSocket reconnection support (`frontends/aiq_api/src/aiq_api/websocket_reconnect.py`), data source toggles, deep research job management, and knowledge base document management
- **Authentication:** Approach I includes JWT-based authentication middleware (`frontends/aiq_api/src/aiq_api/auth/middleware.py`) with path allowlisting for external requests, OIDC issuer verification (`AIQ_JWT_ISSUER`), optional audience validation (`AIQ_JWT_AUDIENCE`), and caller-type detection (JWT, internal, anonymous) propagated via `ContextVar` for downstream logic (e.g., skip clarifier for headless callers)
- **Knowledge layer:** Approach A uses pgvector for RAG; Approach I uses LlamaIndex with ChromaDB (`sources/knowledge_layer/`) for knowledge retrieval, with configurable backend (`llamaindex` or `foundational_rag`), document summary generation via a dedicated LLM (`summary_llm`), and a Knowledge API (`/v1/collections`, `/v1/documents`) for collection and document management
- **Deployment:** Approach A deploys via Helm with ai-architecture-charts subcharts; Approach I provides both docker-compose (`deploy/compose/docker-compose.yaml` with 3 services: aiq-agent, frontend, postgres) and Helm (`deploy/helm/deployment-k8s/`) with pre-built NVIDIA container images (`nvcr.io/nvidia/blueprint/aiq-agent:2.0.0`, `nvcr.io/nvidia/blueprint/aiq-frontend:2.0.0`) or local builds with dev/release build targets

### Typical Components

- **Model serving:** NVIDIA NIM API (cloud-hosted, `https://integrate.api.nvidia.com/v1`) with multiple model configurations -- `nvidia/nemotron-3-super-120b-a12b` for intent classification and research (with `enable_thinking: true`), `openai/gpt-oss-120b` (256K context) for deep research orchestration/planning/writing, `nvidia/nemotron-mini-4b-instruct` for document summarization; no on-cluster model serving required
